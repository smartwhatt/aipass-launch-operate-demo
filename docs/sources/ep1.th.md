 | สวัสดีครับ ลองนึกภาพว่าคุณสร้างแอป AI เสร็จแล้ว เปิดในเครื่องตัวเองก็ใช้งานได้ เลยส่งลิงก์ localhost ให้เพื่อน แต่เพื่อนกลับเปิดไม่ได้ 
url localhost ชี้กลับมาที่เครื่องของคนเปิดลิงก์ครับ แอปที่ทำงานในเครื่องเรา จึงต้องเผยแพร่ก่อนส่งให้คนอื่นใช้
วันนี้เราจะใช้แอปถามตอบคู่มือของ “ศูนย์บริการตัวอย่าง” เป็นกรณีศึกษา พิมพ์คำถาม แอปค้นคู่มือ แล้วตอบพร้อมแหล่งอ้างอิง 
ถ้าคุณเพิ่งเปิดมาดูตอนนี้ ก็เรียนตามได้เลย เราจะเริ่มจากแอปที่เตรียมไว้ แล้วดูว่าก่อนเปิดใช้จริงต้องตัดสินใจและตรวจอะไรบ้าง
 | ภาพผู้สอน → แบ่งจอเครื่องผู้สอนกับเพื่อน เปิด localhost คนละเครื่องให้เห็นผลต่าง
ขึ้นชื่อแอปและป้าย “ข้อมูลสมมติ”
เปิดหน้าแอป ถาม “ศูนย์เปิดกี่โมง” เห็นคำตอบพร้อมเอกสารอ้างอิง

2
 | 01:00–01:45
 | ก่อนเลือกว่าจะเผยแพร่แบบไหน เรามารู้จักสามคำนี้ก่อนครับ
Tunnel คือทางเชื่อมจากอินเทอร์เน็ตเข้ามายังแอปในเครื่องเรา คนอื่นเปิดผ่านลิงก์ที่บริการให้มาได้ เหมาะกับเดโมเร็ว ๆ แต่เครื่องเราต้องเปิดแอปและเชื่อมต่ออยู่
ถ้าจะนำเว็บไปไว้บนระบบให้บริการ (Hosting Service) ก็ต้องดูว่าเว็บทำงานแบบไหน Static คือเว็บที่ส่งไฟล์หน้าเว็บที่เตรียมไว้ให้เบราว์เซอร์เปิด เช่น หน้าแนะนำองค์กร
ส่วน Web app คือเว็บที่ให้ผู้ใช้ทำงานผ่านหน้าจอ เช่น พิมพ์คำถามแล้วให้ระบบค้นคู่มือและสร้างคำตอบ ซึ่งแอปตัวอย่างของเราเป็นแบบนี้ จึงต้องมีทั้งหน้าจอและบริการหลังบ้านรองรับครับ
 | แสดงภาพตามบทพูดทีละแบบ พร้อมชื่อและความหมายสั้น ๆ
1. Tunnel: ผู้ใช้ → ลิงก์ Tunnel → แอปในเครื่องผู้สอน ใส่ไอคอนเครื่องต้องเปิดอยู่
2. Static: ไฟล์หน้าเว็บที่เตรียมไว้ → เบราว์เซอร์ ตัวอย่างหน้าแนะนำศูนย์
3. Web app: ผู้ใช้พิมพ์คำถาม → ระบบค้นคู่มือ/โมเดล → คำตอบ
แยกกรอบ Tunnel ว่าเป็นวิธีเชื่อมเข้าถึงแอป ส่วน Static/Web app อธิบายลักษณะการทำงานของเว็บ ไม่จัดให้เป็นสามหมวดที่ทดแทนกันทั้งหมด
กำกับว่าเว็บ Static อาจเรียกบริการหลังบ้านได้ แต่บริการนั้นต้องเตรียมแยก

3
 | 01:45–02:30
 | นอกจากให้ผู้ใช้เปิดเว็บแอปของเราโดยตรง ยังนำความสามารถของแอปไปให้ใช้ผ่านแอปอื่นได้ครับ
แบบแรกคือ Integration หรือการเชื่อมระบบ เช่น ให้คนถามผ่าน LINE แล้วส่งคำถามไปยังระบบหลังบ้านของเรา ก่อนส่งคำตอบกลับมาใน LINE
อีกแบบคือ Embed หรือฝังหน้าจอ เช่น นำช่องถามตอบไปวางในเว็บภายในหน่วยงาน คนก็ใช้งานได้จากเว็บที่คุ้นเคย ทั้งสองแบบยังต้องมีระบบหลังบ้านรองรับ
สำหรับเดโมนี้ ผมจะเลือกแบบเว็บแอปที่เปิดผ่านลิงก์ได้โดยตรงครับ แล้วจากแอปที่อยู่ในเครื่องเรา ต้องเตรียมอะไรบ้างถึงจะให้คนอื่นเปิดใช้ได้
 | ต่อจากภาพ Web app ในช่วง 2 ขึ้นหัวข้อ “ผู้ใช้จะเข้าถึงแอปผ่านทางไหน”
แสดงสามทางเข้าที่เชื่อมกับระบบหลังบ้านเดียวกัน:
• เปิดเว็บแอปโดยตรง
• Integration: ถามใน LINE → ระบบของเรา → ตอบใน LINE
• Embed: ช่องถามตอบอยู่ในหน้าเว็บภายในหน่วยงาน
ท้ายช่วงไฮไลต์ “เปิดเว็บแอปโดยตรง” แล้วขึ้นคำถาม “จากแอปในเครื่อง → ให้คนอื่นเปิดใช้ ต้องทำอะไรบ้าง”
ยังไม่ขึ้นชื่อ Vercel ในช่วงนี้ ให้คำถามท้ายช่วงพาเข้าสู่การอธิบาย deployment ในช่วง 4

 | 02:30–03:15
 | ตอนที่แอปรันอยู่ในเครื่องเรา โดยเครื่องเราทำหน้าที่รับคำถามและประมวลผลให้ผู้ใช้ครับ ถ้าอยากให้คนอื่นเปิดใช้ได้โดยไม่ต้องเปิดเครื่องนี้ค้างไว้ เราต้องนำแอปไปไว้บนระบบที่พร้อมให้บริการผ่านอินเทอร์เน็ต ขั้นตอนนี้เรียกว่า deploy
เราต้องเตรียมโค้ด ติดตั้ง library ที่แอปต้องใช้ ตั้งค่าการเชื่อมต่อ แล้วเริ่มให้บริการ โดยจะเช่าเครื่องมาดูแลเองก็ได้ หรือใช้แพลตฟอร์มช่วยจัดการ
ในเดโมนี้เราจะใช้ Vercel ครับ เป็นแพลตฟอร์มที่ช่วยนำโค้ดไปสร้างแอปและให้บริการ พร้อมลิงก์สำหรับเปิดใช้ ซึ่งทำให้เราโฟกัสที่การพีฒนาตัวแอปได้มากขึ้น แต่ยังต้องตรวจการตั้งค่า สิทธิ์เข้าถึง และค่าใช้จ่ายของเราเอง
แล้วถ้าจะลองแก้แอป โดยไม่กระทบคนที่กำลังใช้อยู่ เราควรจัดพื้นที่ทำงานอย่างไร
 | เริ่มด้วยภาพ “ผู้ใช้ → อินเทอร์เน็ต → แอปในเครื่องผู้สอน” แล้วเปลี่ยนปลายทางไปเป็นระบบให้บริการภายนอก เครื่องผู้สอนปิดได้ แต่ระบบให้บริการยังทำงาน
ขึ้นคำว่า “Deploy = นำแอปขึ้นระบบให้บริการ”
ไล่ขั้นตอน: โค้ด → ติดตั้งสิ่งที่ต้องใช้/สร้างแอป → ตั้งค่า → เปิดให้บริการ
แนะนำ Vercel พร้อมคำอธิบาย “แพลตฟอร์มช่วยสร้างและให้บริการเว็บแอป” ไม่ใช้โลโก้อย่างเดียว
ภาพ “โค้ดของเรา → Vercel → ลิงก์ให้ผู้ใช้เปิด”
ปิดด้วยคำถาม “จะทดลองแก้แอปโดยไม่กระทบผู้ใช้ได้อย่างไร”
ยังไม่สาธิตปุ่มใน Vercel ให้ไปทำในช่วงเดโม

 | เพื่อให้ทดลองแก้ได้ก่อนเปิดให้คนใช้ เราจะแยกพื้นที่ทำงานเป็นสามแบบครับ
Local คือแอปในเครื่องที่เราใช้พัฒนา Preview คือแอปรุ่นทดลองที่นำขึ้นระบบแล้ว ให้ทีมเปิดลิงก์เข้ามาช่วยตรวจได้ ส่วน Production คือรุ่นที่เปิดให้ผู้ใช้จริง
เวลาแก้แอป เราลองใน local ก่อน จากนั้นส่งขึ้น preview ตรวจการทำงานด้วยข้อมูลสมมติ ถ้าผ่านแล้วจึงปล่อยขึ้น production และตรวจซ้ำอีกครั้ง
แต่ละพื้นที่อาจใช้การตั้งค่าต่างกัน เช่น API key หรือชุดข้อมูลในระบบ เราจึงต้องรู้ว่ากำลังตรวจรุ่นไหนและใช้ข้อมูลชุดใด
ก่อนลงมือ ผมจะให้ AiPASS ช่วยร่างรายการตรวจก่อนเปิดใช้จากบริบทแอปของเรา แล้วอ่านทวนเรื่องงานหลัก สิทธิ์ และข้อมูลลับเองครับ จากนั้นเราค่อยนำรายการนี้ไปใช้กับเดโมบน Vercel
 | ต่อจากคำถามท้ายช่วง 4 แสดง Local / Preview / Production พร้อมความหมาย ไม่ขึ้นสามคำพร้อมกันโดยไม่มีคำอธิบาย
